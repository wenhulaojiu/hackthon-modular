# 普通微信后台发送方案评估

核对日期：2026年11月7日。当前用途为非商业比赛中的研究与验证，目标为Windows微信4.1.15.56。后续若用于商业客服、营销或对外销售，需另行核对授权。

“程序后台运行”“微信位于其他窗口后面”“微信始终最小化”和“无需Windows桌面的服务器接口”是不同能力。HTTP或MCP封装本身不能证明发送不依赖前台。

| 路线 | 已核对证据 | 当前判断 |
|---|---|---|
| [wx4auto](https://wx4auto.lightisle.cn/docs/background/) | 文档介绍UIA与PostMessage；同页也说明不可见时先显示窗口并重建控件树 | 可以作为不占鼠标的候选；不等于一直最小化。其[环境说明](https://wx4auto.lightisle.cn/docs/environment/)记载4.1.15.13可能仅暴露两个UIA节点。本机4.1.15.56也只有基础窗口节点，尚未完成兼容验证。 |
| [WeChatAuto.SDK](https://github.com/scottfly189/WeChatAuto.SDK) | 当前仓库声明支持4.1.9.30以上，提供本机HTTP服务，根许可证MIT | 仍需完整UIA控件树；未核实当前电脑能无焦点发送。不能仅以版本范围认定已适配。 |
| [Prometheus-first/helper](https://github.com/Prometheus-first/helper/blob/main/native/README.md) | 上游声明4.1.15.56文本发送实测；本机Weixin.dll大小与SHA256匹配其[版本矩阵](https://github.com/Prometheus-first/helper/blob/main/native/compatibility.json) | 当前非商业研究的优先候选。源码直接调用微信内部发送流程，推断不依赖前台键鼠；本机后台和最小化发送均未验证。[许可证](https://github.com/Prometheus-first/helper/blob/main/LICENSE)允许非商业研究、测试，商业客服、营销或商业产品集成需另获授权。 |
| [WeChat-Bridge](https://github.com/yuuouu/WeChat-Bridge/blob/main/README.md) | 基于腾讯iLink的Bot通道；用户先给Bot发消息，取得user_id和context_token后才能回复 | 是新的Bot入口，不能据此接管现有个人号好友会话。token有效期由上游控制，连续发送有限制；ret=0仅表示上游接受，未确认送达。 |
| [WeChatFerry](https://github.com/lich0821/WeChatFerry/releases/tag/v39.5.2) / [wxhelper](https://github.com/ttttupup/wxhelper/releases) | 已核对公开版本与文档 | 前者配套3.9.12.51，后者公开适配主要为3.x，不能用作当前4.1.15.56的现成替代。 |
| [微信客服官方接口](https://developer.work.weixin.qq.com/document/path/94677) | 服务器通过客服接口回复会话，不依赖PC窗口 | 适用于客户进入微信客服渠道后的对话，不能直接接管已有个人微信好友聊天。接入前需重新核对企业授权、会话范围及发送规则。 |

目前没有完成“当前电脑、现有个人号、其他程序在前台或微信最小化”的原生发送器实机验收。本次仅阅读官方仓库及只读核对客户端文件指纹，未下载、安装、编译、运行或注入helper，未生成密钥或读取聊天正文，也未调整系统安全设置。

## helper的证据与最小接入方案

以下三种证据不能混用：

- **上游声称实测**：[原生说明](https://github.com/Prometheus-first/helper/blob/main/native/README.md)列明4.1.15.56账号发现、文本发送、其他账号发来的群文本、撤回关联及桥接加载与卸载；没有明确列出最小化或其他应用位于前台时的发送实测。
- **源码推断**：[text_service.py](https://github.com/Prometheus-first/helper/blob/main/native/text_service.py#L798)经[run_selftest.py](https://github.com/Prometheus-first/helper/blob/main/native/run_selftest.py#L432)调用DLL导出WxSendText，再由[text_bridge.cpp](https://github.com/Prometheus-first/helper/blob/main/native/text_bridge.cpp#L251)调度微信自身发送任务。这条链不使用模拟键鼠或前台窗口检查，支持“不依赖焦点”的判断；不能替代本机验收。
- **本机已核对**：Weixin.dll为204305968字节，SHA256为`e0428a7b691853de496532523c2c09aa095f90941c37c9f4cfb3f137f3c66556`，与上游4.1.15.56条目一致。只证明符合其构建指纹，不证明发送成功或长期稳定。

按[快速开始](https://github.com/Prometheus-first/helper/blob/main/docs/guide/quick-start.md)，运行需要Windows 10/11 x64、64位Python（作者验证3.13）、Microsoft Visual C++ x64运行库，以及requirements.txt中的Python依赖。仓库直接附有text_bridge.dll、selftest_bridge.dll等预编译文件，目前没有GitHub Release；这些是仓库内二进制，未在本机验真或执行。使用已有DLL无需Visual Studio；重新构建才需要MSVC x64工具链，见[构建脚本](https://github.com/Prometheus-first/helper/blob/main/native/build_bridges.ps1)。

普通文本原生收发不要求第三方机器人平台、模型密钥或云服务。模型与Fish Audio语音属于可选功能。本机管理台默认监听127.0.0.1:8765，关闭浏览器不停止机器人；启动机器人会加载桥接并建立接收Hook，不能把启动视为纯检查。最小比赛试验只保留目标会话收发，关闭默认自动回复、防撤回补发及其他业务插件，沿用客序现有决策逻辑。

现有[HTTP路由](https://github.com/Prometheus-first/helper/blob/main/wxbot_framework/panel_http.py)已提供文本入口，API要求X-Helper-Token，并核对Host及Origin；多账号请求需指定`?robot=对应工作区`。只读取得当前连接后才能提交发送：

| 接口 | 参数或返回含义 |
|---|---|
| GET /api/send-connection | 返回当前session_id；断线或切号后旧连接不可复用 |
| POST /api/send-text | JSON含chat_id、content、request_id、session_id，可选at_list；request_id为16—80位字母、数字、下划线或连字符 |
| GET /api/send-status?id=请求编号 | 查询sending、sent或failed；sent仅反映该发送流程完成 |

[管理台实现](https://github.com/Prometheus-first/helper/blob/main/wxbot_framework/web_panel.py#L753)对相同request_id与相同载荷返回旧任务，冲突载荷拒绝；但只在内存保留最近64条，重启会丢失，不能承担客序的持久幂等。Python接入也可使用NativeTextBackend与Service的expected_session检查，避免绕开连接隔离；底层NativeTextService单条限制1023个UTF-8字节，上层Service才会按字符边界分段。

发送结果需要另做数据库回读。[原生回调](https://github.com/Prometheus-first/helper/blob/main/native/text_bridge.cpp#L131)只检查回调结果首字节并写target、text及completion_success；[Python判断](https://github.com/Prometheus-first/helper/blob/main/native/run_selftest.py#L525)再核对正文、目标和任务清理，没有返回发出消息的native/server message ID，也没有查询微信数据库。管理台消息监控中的bot_generated记录是[SDK合成记录](https://github.com/Prometheus-first/helper/blob/main/wxbot_framework/sdk.py#L81)，不能当作微信落库证据，更不能当作对端送达证据。

具体集成时保留客序的账号与唯一chatId，只把发送适配器替换为本机helper入口；显示昵称不参与路由。客序先将outbox编号、账号、chatId、连接、正文摘要及发送前数据库游标持久保存，串行提交一次；原生完成后，通过现有只读数据库链按账号、会话、自发方向、准确正文和新增消息ID回读，再记录confirmed。若超时、断线、长文部分发送或回读不确定，标记unknown并人工核对，重启后先回读再决定是否处理，禁止自动重复发送。长文应逐段记账验收。

后续最小实机验收应使用自有测试账号和固定会话，分别验证其他程序在前台、微信最小化、客户端重连、服务重启及切号停止；每次都以真实数据库新增记录为依据。当前仅形成可实施方案，未执行上述操作。

已有本机视觉发送只支持已校准窗口。临时单会话网关的状态可以区分组件可配置与窗口是否位于前台；这并没有赋予视觉发送器后台输入能力，实际输入与点击仍须前台核验。

若继续使用视觉发送，可考虑在专用Windows电脑或独立虚拟机桌面中运行，让该桌面的微信保持可操作；这属于部署隔离，需要独立验收。当前比赛可先验证helper；将来转向商业使用时，再取得明确的当前版本支持与商用授权。
