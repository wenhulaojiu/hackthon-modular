## 复制来源

本仓库从私有仓库 `wenhulaojiu/hackthon` 的提交 `1bcd2f97a14e07dd797e6924fde8ed5716b46bbe` 复制，并保留该分支已有 Git 历史。所有整理发生在新仓库，旧仓库未修改。本仓库后续与旧仓库独立维护，不会自动双向同步。

## 如何分配任务

1. 在任务中写明页面名称和 `features/<模块>/` 目录。
2. 写清允许修改的关联 `lib/` 或接口文件、预期行为和验收条件。
3. 提交前运行 `npm run typecheck`、`npm test`、`npm run build`。
4. 修改公共类型、全局样式、权限、数据库或发送逻辑时，先与其他模块负责人协调。

示例：“修改 `features/customers/` 的客户详情展示；验收客户排序和详情打开；涉及 `lib/types.ts` 时先协调。”

`.github/CODEOWNERS` 当前由仓库所有者统一负责，注释中给出了按模块分配的方式。添加真实队友后再替换账号，避免填写不存在的负责人。目录归属用于分工与审核，不限制仓库成员读取其他目录。

当前沿用项目 AGENTS.md 的直接提交 main 约定。若团队改用 PR，应同时更新该约定，并在 GitHub 规则集要求负责人审核和 CI 通过。CODEOWNERS 和 CI 文件本身不等于启用了分支保护；本次没有改变仓库成员、规则集或部署权限。

## 安全措施与边界

- 仓库保持 Private；只给需要的人仓库权限。需要隔离可见代码时应使用不同私有仓库。
- `.env`、`.dev.vars`、运行数据库、聊天记录、账号配置、日志、第三方原生程序不提交。只保留无真实凭据的 `.env.example`。
- `.github/workflows/checks.yml` 自动运行类型检查、现有测试和构建；工作流只授予读权限。
- Dependabot 每周检查 npm 和 GitHub Actions 依赖；更新仍需维护者确认兼容性。
- API 的登录校验、工作空间归属、模型密钥加密、本地接口访问限制由既有实现负责，本次仅整理目录，没有把这些实现当作已完成安全审计。
- 涉及客户资料、真实微信发送的验收必须在授权的测试数据与测试账号上进行；此次不启动真实微信或发送程序。
- 发布前单独核查跨账号访问、外部模型地址限制、导入限制、发送接管、日志脱敏、备份恢复及依赖漏洞。
- 曾公开过的密钥即使仓库后来改为私有也应撤销更换；仓库私有不能撤回其他人已有的克隆。

安全问题请通过仓库所有者的私密渠道报告，不在公开议题或 PR 中粘贴真实聊天、凭据或客户数据。
